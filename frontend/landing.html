How it works

Retrieval first. Then an answer.

DocMind doesn't hand your whole PDF to a model and hope. It finds the few passages that actually answer your question and answers from those alone.

Once per PDF Ingestion

  1. Extract

    Text is pulled from every page with PyMuPDF, keeping page numbers.

  2. Chunk

    Split into 100-word passages with a 20-word overlap.

  3. Embed

    A small local model turns each passage into a vector.

  4. Store

    Vectors are saved to ChromaDB on disk, tagged with their page.

Every question Answering

  1. Ask

    Your question is embedded with the same local model.

  2. Retrieve

    The 3 closest passages are found by cosine similarity.

  3. Ground

    Those passages, with page tags, become the model's only context.

  4. Answer

    A local LLM writes the answer and DocMind lists the source pages.

Features

Built for documents you need to trust

Contracts, research papers, manuals, reports — anywhere a wrong answer costs you.

Page citations

Every answer lists the pages it was drawn from, so you can open the PDF and verify it yourself.

Private by default

Embeddings, search and generation all run on your hardware. Your document never leaves the machine.

Confidence floor

If nothing in the document is close enough to your question, DocMind says so — without calling the model at all.

Fast to ingest

A lightweight embedding model indexes long PDFs on a regular CPU. No GPU required.

Plain-language chat

Ask follow-ups the way you'd ask a colleague. Drag in a PDF and start typing.

Small and hackable

FastAPI, ChromaDB and plain HTML/CSS/JS. No build step, easy to read, easy to change.

Grounded answers

"I couldn't find that" is a feature.

Before any answer is written, DocMind measures how close the best passage is to your question. If it's too far — a cosine distance above 0.5 — you get an honest "not found" instead of a confident guess.

When the model does answer, it's told to use the retrieved context and nothing else.
